Trauma Activation Schema Report

8 October 2026 · Ahmad Mohammad Odeh Ali

Summary

The handover schema is now a Pydantic model that can represent every one of the 37 criteria in the 2024 adult trauma activation document (16 Level I, 13 Level II, 8 Level III). A test checks this automatically. Since the first version of this report, a worked radio case and a JSON-LD layer have been added, and all 79 tests pass.

The schema follows IMIST-AMBO and keeps three rules throughout: an unmentioned field is None and never a negative, units stay as the source document uses them (feet, mph, inches), and the record holds what the crew said, not the patient's true state.

The source document

The criteria assign a hospital trauma team activation level, not a transport destination. That makes them a closer fit for the thesis than the 2021 Field Triage Guideline, because the thesis output is exactly this pre-arrival activation decision.

  • Scope: adults aged 15–64, updated February 2024. The document references EPIC, so it comes from a US hospital.
  • Level I (trauma surgeon within 20 minutes): 16 criteria on physiology, airway and chest, hemorrhage, anatomic injury, burns and transfusion-dependent transfers.
  • Level II: 13 criteria, mostly mechanism of injury (falls, vehicle crashes) and less severe anatomic injury.
  • Level III (trauma note in EPIC): 8 criteria for low-risk mechanisms and minor injuries.

The 2021 Field Triage Guideline stays useful as background, but the rule engine should implement this document if it is the protocol your supervisor wants to target.

Schema design

The top level follows the IMIST-AMBO order. Each section holds only what at least one criterion, or the handover protocol itself, needs.

SectionModelFields the criteria use
IdentificationIdentificationage, sex, pregnancy and gestation, arrival mode (scene, interfacility transfer, walk-in), ETA
MechanismMechanismmechanism type (16 values), fall type and height in ft, vehicle crash details, loss of consciousness and its duration
InjuriesList[Injury]injury type, body region, side, suspected, bone, open fracture, depressed skull, unstable pelvis, digits amputated
BurnsBurns% total body surface area, inhalation injury, electrical
SignsSigns, Vitals, GCSSBP, HR, RR, SpO2 and whether on room air, GCS and whether taken before intubation, airway status, flail chest, hemo/pneumothorax, shock signs, hemorrhage, paralysis, sensory loss, suspected cord injury, abdominal findings, trend
TreatmentTreatmentinterventions (15 values), transfusion needed to maintain vitals
Allergies, Medications, Background, Otherlists and free textnone, kept for the protocol
CorrectionsList[Retraction]the retracted and corrected value for contribution C4

Four design decisions shape the whole schema:

  • Not mentioned is None, not a negative. Booleans are three-valued: occurred: False means the crew said there was no loss of consciousness, while None means nobody mentioned it. Lists work the same way: allergies: None is "not mentioned", allergies: [] is "no known allergies".
  • Source units. Fall height is in feet, speed in mph and intrusion in inches, so each rule can be read directly against the document's thresholds.
  • Measurement context is stored with the value. Two Level I criteria depend on it: SpO2 counts only on room air (spo2_on_room_air), and GCS counts only before intubation (before_intubation). A bare number would be ambiguous.
  • Body regions map to the document's landmarks. The criteria use "t-shirt/boxer area" and "proximal/distal to wrist or ankle". The schema records 23 ordinary body regions, and vocab.ZONE_OF_REGION maps each one to head, neck, t-shirt/boxer area, proximal limb or distal limb. The extractor reports where the injury is; the rule engine decides which zone that falls in.

Validation rules

The grammar used for constrained decoding can only guarantee that the output has the right shape. These validators catch outputs that parse but contradict themselves, and each one has a test that feeds it a bad record and expects a rejection.

RuleRejects
Unknown fields forbidden (extra="forbid")Any field the schema does not define
Physiological rangese.g. HR above 300, GCS total outside 3–15, % body surface above 100
GCS components sumEye + verbal + motor that does not equal the stated total
SpO2 contextspo2_on_room_air given with no SpO2 value
Blood pressureDiastolic higher than systolic
Fields fit the injury typeA bone or open-fracture flag on a non-fracture, depressed on a non-skull fracture, pelvis_unstable on a non-pelvic fracture, digit count on a non-amputation
Bone matches regionA femur fracture recorded on the upper arm, a skull fracture on the chest
Limb-only findingsA pulseless, mangled or degloved "extremity" on the torso
Mechanism details fit the mechanismFall details on a stabbing, vehicle details on a gunshot, a fall height on a same-level fall
LOC durationA duration given when LOC was denied
PregnancyPregnant and male; gestation weeks without pregnancy
ShockShock signs listed while shock is recorded as absent
Treatment against signsAn advanced airway placed while airway is recorded as patent; a tourniquet with hemorrhage recorded as none

In the pipeline, a rejected record goes back to the model with the validator's message, up to a capped number of retries. If it still fails, the system asks the crew for the missing information rather than guessing.

Worked example: a radio handover

One realistic call was written out and converted by hand into a HandoverRecord to test the schema on radio speech. It validates, and it is included in the test suite.

Memorial ED, Medic 14, how copy? ... Copy Memorial, we're inbound to you priority one, ETA about twelve minutes. We've got a thirty-two-year-old male, motorcyclist versus car, estimated speed around forty-five miles an hour. Patient was separated from the bike and thrown roughly twenty feet, he was helmeted. Bystanders report a brief loss of consciousness on scene, under a minute. Injuries: open right femur fracture, mid-shaft, bleeding is controlled with a pressure dressing. Deformity to the left wrist, and some abrasions to the left flank. No other obvious injuries. Vitals: BP eighty-eight, uh, correction, one-oh-eight over sixty-two. Heart rate one-eighteen, resps twenty-four, sats ninety-five percent on room air. GCS fourteen, that's eyes four, verbal four, motor six, he's a bit confused, keeps asking what happened. Skin is pale and clammy. Treatment: traction splint to the right leg, splinted the left wrist, he's in a collar with full spinal precautions. Two large-bore IVs, five hundred of saline running, and fifty micrograms of fentanyl for pain. No known allergies. He's been stable en route. Any questions?

Conversion decisions worth noting:

SpokenRecorded asWhy
"Deformity to the left wrist"Fracture, suspected: true, no boneThe medic described a deformity, not a diagnosis
"Under a minute" LOCduration_minutes: 1An upper bound, but well below the 5-minute threshold either way
"Pale and clammy"shock_signs filled, clinical_signs_of_shock: nullThe medic never said "shock"; the term is undefined in the criteria
"No known allergies"allergies: []Stated as none; medications and history were never mentioned, so they are null
Pressure dressinginterventions: otherNo enum value exists; add pressure_dressing if dressings are common
"BP eighty-eight, uh, correction, one-oh-eight"SBP 108, plus a retraction of 88The corrected value is the one the record keeps

Activation level: Level II, from L2-04 (motorcycle at 45 mph with rider separation), L2-06 (one femur fracture) and L2-07 (open fracture proximal to the ankle). No Level I threshold is met. The correction shows why contribution C4 matters: if an extractor kept the retracted 88, SBP < 90 with pale, clammy skin would meet L1-02 and the patient would move to Level I.

JSON-LD layer

JSON-LD is added as a separate output layer, not inside the extraction schema. The model still decodes the plain JSON Schema, which keeps the grammar small; after validation, to_jsonld() adds @context, @id, an @type on every section and a timestamp.

The context and vocabulary are generated from the Pydantic models rather than written by hand, so they cannot drift from the schema; a test fails if they are out of date. The vocabulary defines 13 classes and 14 code lists, and it also holds knowledge the criteria need as data: each body region's anatomic zone, and which bones count as long bones.

TerminologyCoverageStatus
LOINC11 codes: systolic and diastolic BP, heart rate, respiratory rate, SpO2 by pulse oximetry, GCS total and its three components, age, sexEach code checked against the NLM Clinical Tables LOINC API on 8 October 2026
UCUM15 fields, e.g. mm[Hg], /min, [ft_i], [mi_i]/h, [in_i]Done
SNOMED CT8 code lists marked for binding: mechanisms, injury types, body regions, bones, interventions, shock signs, airway status, hemorrhageEmpty until the UMLS licence is in place; no unverified codes were written

Two problems surfaced and were fixed:

  • JSON-LD silently drops unknown keys. A field missing from the context simply disappears, with no error. A test converts every example to RDF and checks that the number of stated values equals the number of triples. Removing a single term from the context turns 45 values into 44, and the test fails.
  • RDF cannot express an empty list. allergies: [] ("no known allergies") and null ("not mentioned") would both produce no triples. The JSON-LD view therefore adds allergiesStated, medicationsStated, backgroundStated and injuriesStated flags. In the radio case, allergiesStated: true with no allergies listed means none known.

Values that share a name stay distinct, because each enum value gets its own IRI: Ejection.none and Hemorrhage.none are separate concepts. The namespace https://w3id.org/radio-to-resus/vocab# is a placeholder; register it on w3id.org, or switch to a URL you control, before publishing the corpus.

Next steps for data generation

The schema fixes what the data generator must produce: two records per handover, one for the patient's true state and one for what the crew said, both valid HandoverRecords.

  1. Settle the ambiguities above, at least the t-shirt/boxer boundary, before any labels are generated. Every triage label depends on them.
  2. Sample cases so every level and most criteria appear. The criteria are the natural sampling frame: include borderline cases on purpose (SBP 88 and 92, falls of 19 and 22 ft), because that is where extraction errors flip decisions.
  3. Check which fields the datasets actually provide. NEMSIS should cover mechanism, vitals and procedures. Crash details such as intrusion in inches and extrication time may not exist there and would have to be sampled.
  4. Add the enum values the radio case exposed, starting with pressure_dressing, and keep converting a few realistic calls by hand to find more gaps before generating at scale.
  5. Write the rule engine against criteria.yaml. It can be built and tested on hand-made records now, without waiting for data access, and it produces the ground-truth label for every generated case.

To regenerate the examples and JSON Schema, run scripts/make_examples.py with the project's .venv Python. After any schema change, also run python -m schema.jsonld.build and scripts/make_jsonld_examples.py. To check everything, run pytest.
